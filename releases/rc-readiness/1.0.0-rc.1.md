5. Front-matter and schema identifiers were prose-only claims; immutable identifier checkpoints plus mutation/removal tests were added.
6. Normative-rule enforcement initially covered only governance and C#; coverage was broadened across the published repository rule surface.
7. The first broadened rule gate still omitted non-governance/non-C# package families; immutable published-source derivation now covers the complete numbered rule surface.
8. Public tool finding-code values and meanings were not pinned; a published finding-code compatibility checkpoint and emitted-code exercises were added.

10. Root `README.md` similarly overstated exact-tree validation and was corrected.
11. The published profile checkpoint omitted the 13 stable profile package directories; all 13 files plus all 13 directories are now enforced with correct types.
12. Finding-code tests initially checked literal presence without binding codes to published emission semantics; semantic comparison against immutable published source was added.
13. Stable C# coverage initially bound only ten summary rules; the complete promoted `languages/csharp/standards/` tree is now tied to immutable promotion evidence.
14. Finding semantics initially omitted referenced constants/dataflow such as `REQUIRED_RELEASE_HEADINGS`; those dependencies are now included.
15. A non-finding `git_output(...)` helper could suppress `RELEASE_HEAD_TAG_MISSING` without changing caller AST; focused runtime coverage was added.
16. `MANIFEST.md` still overstated permanent validation for the exact current tree and now limits the claim to the recorded functional candidate.
17. The first `git_output(...)` runtime regression covered only the missing-tag outcome; a real tagged Git repository fixture now covers the success path too.
18. Published agent-skill entry points, including `languages/SKILL.md`, were not independently anchored; all seven published routes are now checkpointed against the immutable `v0.10.0` root manifest.
19. **P1:** the earlier normative-rule remediation over-constrained compatible changes by requiring broad package/tree Git identities. It now derives and compares published **path + ID + requirement meaning** occurrences from immutable `v0.10.0` source. Published scoped duplicate IDs are grandfathered, new unique rules are allowed, and new reuse is rejected.
20. **P1:** the earlier finding-code remediation over-constrained compatible validator fixes by requiring whole tool-directory identities. Those directory hashes are removed; the gate now derives and preserves published production finding semantics directly from immutable `v0.10.0` Python sources while allowing unrelated compatible changes.
21. **P1:** new-rule reuse detection initially collapsed occurrences to distinct paths, so two copies of a new identifier in the same file could evade the duplicate check. The rule gate now counts occurrences and includes an explicit same-file duplicate regression.
22. **P1:** finding semantic signatures initially followed constants and local data but not referenced module-level helper implementations. Helper bodies now participate in semantic dependency fingerprints. The already-intentional `read_release_state()` strengthening is explicitly pinned to reconciliation commit `a96d6a92da40257cbe4c6e0fe0c7bbbd397adef3` and projected only for its two affected published findings, so future helper changes still fail.
23. **P1:** the result-schema compatibility test initially required the candidate schema file to retain the exact `v0.10.0` SHA-256, incorrectly rejecting compatible optional additions. The immutable hash now authenticates the published source only; current compatibility is structural and allows optional properties/editorial annotations while rejecting breaking required/type/enum/extension/property-removal/narrowing changes.
24. **P2:** the first AST finding-code comparison froze human-readable message wording. Message text is now excluded while stable semantic context, helper/data dependencies, and non-message emission behavior remain enforced.
