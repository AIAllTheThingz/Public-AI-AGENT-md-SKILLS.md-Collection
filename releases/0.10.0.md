This document prepares the first forward-only publication after the unpublished `0.9.0` baseline. It does not authorize or imply that `v0.10.0` exists.

Publication requires a dedicated final preparation step that moves the canonical repository `VERSION` to `0.10.0`, finalizes the dated changelog entry, validates the exact source commit, builds deterministic artifacts, receives the required independent review, and only then creates the tag.

The current repository state also enforces the historical boundary in code: `releases/release-state.json` marks `0.9.0` as prepared/unpublished, release tag validation rejects that version, and the builder refuses to construct publication artifacts for it.

## Breaking changes

- Repository-maintenance approval behavior changes relative to the prepared `0.9.0` governance contract: low- and moderate-risk routine repository changes may be maintainer self-reviewed after permanent CI when no independent-review gate applies. Independent review remains mandatory for high/critical risk, breaking repository changes, the final `1.0.0` compatibility approval, stable-maturity commitments, and explicit exception gates.
- Canonical schema and tool-result `$id` values move from raw GitHub URLs under the former `AIAllTheThingz/Public-Access-Agents` repository path to `AIAllTheThingz/Public-AI-Governance`. Schema structure, required fields, property types, and instance validation behavior are unchanged, but consumers that persist or compare exact `$id` strings must migrate those identifiers.
- Narrowed the supported Oracle Linux Virtualization Manager (OLVM) boundary: OLVM is treated as a legacy managed boundary tied to supported Oracle Linux 8 estates and must not be inferred as the management plane for Oracle Linux 9/10. Adopters that previously applied the prepared 0.9 guidance to OLVM-managed Oracle Linux 9/10 environments must migrate or re-scope that adoption.

The repository-maintenance item does not weaken adopter-facing engineering, security, testing, validation, or completion-evidence standards. The machine-readable identifier migration and OLVM platform-boundary narrowing are explicitly classified as breaking under the repository release policy and are covered by the migration guidance below.

## Pre-publication validation

Before creating `v0.10.0`, the final release-preparation commit must set `VERSION` to `0.10.0`, finalize the changelog entry, and then run from the exact candidate source commit:

```bash
python -m pip install --require-hashes -r tools/validate-schemas/requirements.lock
python tools/validate-all/run_all.py --include-tests
python tools/release/validate_release.py --tag v0.10.0
python tools/release/build_release.py --tag v0.10.0 --output-dir dist --force
```

Verify:

```bash
cd dist
sha256sum -c SHA256SUMS.txt
```

The breaking `$id` migration requires independent specialist review before publication. Tag creation and GitHub Release publication must remain separate from preparation until those checks and required reviews are complete.
