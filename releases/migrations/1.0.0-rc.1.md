# Migration to 1.0.0-rc.1 from 0.10.0

## Who is affected

Adopters intentionally evaluating the `1.0.0-rc.1` compatibility candidate from published `v0.10.0`, existing SRE or Testing package adopters, existing canonical-profile adopters whose scope satisfies a Product Management or User Experience predicate, and maintainers reviewing the intended first stable repository contract.

Existing `v0.10.0` consumers are not forced to move to this prerelease.

## Required actions

1. Record the exact `1.0.0-rc.1` source commit or published prerelease tag used for evaluation; do not relabel `v0.10.0` evidence as RC evidence.
2. Existing SRE adopters must add `SRE-READINESS-006` and `SRE-SCALING-007` to tailored instructions; assess every production-readiness and scaling-strategy area; keep Data migration, Privacy, and Security as independent decisions when applicable; record per-area plus overall readiness evidence for the exact candidate and operating scope; record representative scaling validation that misses authorized criteria as `Failed` rather than unresolved; and withhold an overall scaling-strategy `Verified` claim until every applicable area is `Verified` with no `Applicable`, `NotRun`, `Blocked`, or `Failed` area.
3. Existing Testing adopters must add `TEST-PERFORMANCE-006` to tailored instructions and assess baseline, load, stress, spike, soak or endurance, scaling, failure-under-load, and recovery-under-load applicability. For each test type, record execution state separately from `Pass`, `Fail`, `Blocked`, or justified `NotApplicable` outcome; record the owner, explicit execution authorization and safeguards, safe stop conditions, representative workload and environment, authorized criteria, primary results, and recovery evidence. A performance or scalability validation claim requires every applicable test type to have state `Tested` and outcome `Pass`.
4. Existing profile adopters of `AI_AGENT_APPLICATION`, `CLI_TOOL`, `DATA_PIPELINE`, `DESKTOP_APPLICATION`, `INTERNAL_AUTOMATION`, `MOBILE_APPLICATION`, `MULTI_TENANT_SAAS`, `PUBLIC_LIBRARY`, `SECURITY_TOOL`, `SERVERLESS_FUNCTION`, `WEB_API`, `WEB_APPLICATION`, or `WORKER_SERVICE` must re-evaluate every selected primary and secondary profile against its conditional Product Management and User Experience predicates.
5. Select Product Management when the affected profile scope defines or materially changes its product capability, outcome, requirements, supported scope, MVP boundary, acceptance criteria, or product decisions. Select User Experience when the affected scope owns human goals, journeys, tasks, prompts, approvals, interactions, recovery states, interfaces, or UX-validation claims. If a predicate is not satisfied, retain a scope-specific omission rationale; profile selection alone is insufficient to select either overlay.
6. When a predicate is satisfied, add the corresponding `product-management` or `user-experience` discipline to the project manifest and composed standards, then synchronize the decision across the complete profile README, adoption checklist and example, root and nested `AGENTS.md`, tailoring record, and completion evidence. For a selected User Experience package, record validation state separately from per-method and overall outcome and withhold a UX-validated claim unless the overall outcome is `Pass` and every applicable method and claim succeeds for the exact interface version and representative conditions. `--include-profile-required` does not select conditional overlays automatically.
7. Treat `languages/csharp` as the only package in the initial stable package promise. All other packages remain `baseline` unless a later evidence-backed promotion says otherwise.
8. If automation consumes schema `$id` values, stable template paths, tool entry paths, exit codes, JSON result fields, or release artifact names, retain those contracts or document any explicit candidate incompatibility before adoption.
9. Re-run repository and project validation appropriate to every adopted package after changing the pinned standards source. Adopters unable to complete newly required package and evidence work must retain their prior pin or record the migration as `Blocked`; they must not claim conformance to this RC.

## Optional improvements

- C# adopters may use the direct `csharp` skill and its registered agent interface while preserving root governance and scoped `AGENTS.md` authority.
- Windows PowerShell 5.1 adopters may adopt the new legacy compatibility overlay where their project contract genuinely requires `powershell.exe`.
- Mixed-profile projects using `generate-manifest --include-profile-required` may regenerate manifests so selected secondary profiles contribute their discipline links.

## Removed or deprecated contracts

No contract is removed or deprecated relative to published `v0.10.0`.

No `v0.10.0` stable schema major path, original stable template path, stable tool entry path, or documented release artifact name is intentionally removed by this candidate. The breaking changes instead strengthen existing baseline package and profile-adoption contracts for affected adopters.

## Compatibility assumptions

- `v0.10.0` is the published migration checkpoint and source boundary.
- The candidate is breaking for existing SRE and Testing adopters and for existing canonical-profile adopters whose scope satisfies a Product Management or User Experience predicate; unaffected adopters may retain justified omissions where the updated standards permit them.
- The RC compatibility inventory at `releases/compatibility/1.0.0-rc.1.json` is the machine-readable statement of the intended stable surface.
- Repository paths can remain compatibility-sensitive even when the package they belong to is still `baseline`; baseline maturity means the package is outside the stable package promise, not that maintainers may silently break documented contracts.
- Final `1.0.0` has not yet been approved or published.

## Validation commands

```bash
python -m pip install --require-hashes -r tools/validate-schemas/requirements.lock
python -m unittest discover -s tools/tests -p "test_rc_compatibility_gate.py" -v
python tools/validate-all/run_all.py --include-tests
python tools/release/validate_release.py --tag v1.0.0-rc.1
```

The tag validation command validates the candidate contract; it does not create or publish a tag.

## Rollback or downgrade considerations

An adopter can return to the published `v0.10.0` source boundary by restoring that pin, restoring or regenerating the prior tailored composition, and revalidating derived artifacts. Do not mix RC-only requirements or maturity claims with evidence attributed to `v0.10.0`, and do not present downgrade as proof that newer readiness or testing obligations were satisfied.

## Unresolved limitations

- A source candidate does not satisfy the final `1.0.0` requirement that at least one RC be published and available for review.
- Qualified independent specialist review of the breaking package and profile changes on the exact final release head is required before merge, tagging, or publication; automated review and earlier approvals do not satisfy that gate.
- Independent artifact/checksum verification remains required before final `1.0.0`.
- Final `1.0.0` compatibility approval remains a separate independent-review gate.
- GitHub-host controls recorded as Blocked/manual remain outside repository-source validation.
