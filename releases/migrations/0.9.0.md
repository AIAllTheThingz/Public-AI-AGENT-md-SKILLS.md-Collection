# Migration Notes for 0.9.0

## Publication state

Version `0.9.0` was prepared as the initial pre-1.0 compatibility baseline but was never published. There is no `v0.9.0` Git tag and no `0.9.0` GitHub Release.

These notes therefore describe the prepared baseline and the migration intent of that repository state. They are not proof that a published `0.9.0` source boundary exists.

## Audience

These notes apply to people who copied standards, templates, schemas, or tools from the repository around the prepared `0.9.0` baseline.

## Summary

The prepared `0.9.0` baseline established the initial pre-1.0 compatibility model as repository content.

It did not remove or rename existing public standards packages, schemas, templates, profiles, examples, or executable tool entry points.

Because the tag was never created, adopters must identify the exact source commit or copied bundle they actually used rather than claiming a `v0.9.0` source tag.

## Required actions

Existing adopters should:

1. Record the exact source repository commit or copied bundle actually used by their project.
2. Do **not** record `v0.9.0` as the source tag unless a future historical recovery deliberately creates that tag at the correct historical commit.
3. Treat `0.9.0` as a prepared compatibility baseline, not as a published GitHub Release.
4. Review [`RELEASE_POLICY.md`](../../RELEASE_POLICY.md) for compatibility and deprecation behavior.
5. Review [`MATURITY_POLICY.md`](../../MATURITY_POLICY.md) before treating a package as stable.
6. Continue using major-version schema paths under `schemas/v1/` for durable automation; pin an actual source commit when exact schema immutability is required.
7. Run the repository validation tools after copying or updating standards.
8. Review the future `0.10.0` release notes before moving to the first forward publication after the prepared baseline.

## Optional improvements

- Use `tools/generate-manifest/generate_manifest.py` to create a version-aware project manifest.
- Use `tools/compose-agents/compose_agents.py` to create a traceable standards bundle.
- Store the source repository commit and selected package versions with completion evidence.
- Compare future published releases against their real tags rather than an unversioned branch snapshot.

## Removed contracts

None.

## Deprecated contracts

None.

## Compatibility assumptions

- Existing stable file paths remain present.
- Existing rule identifiers remain present.
- Existing schemas remain available under their rolling and `v1` paths.
- Existing tool entry points remain present.
- Most packages remain `baseline`, not `stable`.
- No immutable `v0.9.0` source commit is implied by these notes.

## Validation

From a historical checkout intended to represent the prepared baseline, the release program was designed to use:

```bash
python -m pip install -r tools/validate-schemas/requirements.txt
python tools/validate-all/run_all.py --include-tests
python tools/release/validate_release.py --tag v0.9.0
```

Do **not** use current `main` to retroactively create `v0.9.0`. Current `main` contains later work intended for the forward-only `0.10.0` release.

For an adopting project, re-run its own tests, link checks, schema validation, and project-specific review after updating copied standards.

## Downgrade and rollback

Because no `v0.9.0` tag exists, rollback must use the exact previously recorded commit, archive, or copied standards bundle.

Do not reconstruct the previous state from memory and do not assume current `main` is equivalent to the prepared `0.9.0` baseline.

## Known limitations

- `0.9.0` was never published as a Git tag or GitHub Release.
- The repository has not yet published the final `1.0.0` compatibility commitment.
- Package-level adoption testing and stable maturity promotion remain ongoing.
- Repository release checks do not validate an adopting project's environment.
