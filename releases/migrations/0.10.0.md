# Migration Notes for 0.10.0

## Publication state

Version `0.10.0` is the intended next forward publication after the prepared-but-unpublished `0.9.0` baseline. These notes are prepared in advance of publication; no `v0.10.0` tag or GitHub Release exists until the final release process deliberately creates them.

## Audience

These notes apply to adopters moving from an earlier repository commit or copied Public Access Agents standards bundle to the future `0.10.0` publication.

## Summary

The intended `0.10.0` release is primarily additive. It expands language, virtualization, operating-system, networking, skill-routing, manifest, validation, and release-maintenance capabilities while adopting a lighter repository-maintenance review model.

The canonical GitHub repository is `AIAllTheThingz/Public-AI-Governance`. The project/library name remains **Public Access Agents**, and release archives retain the `Public-Access-Agents-<VERSION>` prefix.

## Required actions

Adopters should:

1. Record the exact published `v0.10.0` tag or source commit after publication; do not record `v0.9.0`, because that tag was never created.
2. Update repository links and raw-content URLs to `AIAllTheThingz/Public-AI-Governance` when maintaining local documentation or automation.
3. If automation persists exact schema `$id` values from the former `Public-Access-Agents` raw GitHub path, update those identifiers to the corresponding `Public-AI-Governance` paths and re-run schema integration tests.
4. Re-run repository or project validation after updating copied standards, schemas, templates, or tools.
5. Add `languages/csharp` when C# source is in scope; modern C# projects normally compose the C# language package with the .NET package.
6. If using `virtualization`, `operatingSystems`, or `networking` project-manifest selections, emit `schemaVersion: "1.1.0"` and use compatible manifest/composition tooling.
7. Review infrastructure package selections explicitly rather than silently assuming virtualization, operating-system, or networking standards do not apply.
8. For PowerCLI users, inventory current modules and verify the supported VCF PowerCLI migration/compatibility path before changing operational automation.
9. Review the repository-maintenance governance change separately from adopter-facing engineering standards; routine repository self-review does not waive project-specific review or production authorization requirements.
10. Treat XenServer 9 as the current GA family for new XenServer guidance; classify XenServer 8 and Citrix Hypervisor references as installed-estate, compatibility, or migration boundaries rather than greenfield defaults.
11. Treat Red Hat Virtualization as Extended Life legacy/migration scope. Do not assume normal bug fixes, security fixes, hardware enablement, or root-cause analysis continue; evaluate OpenShift Virtualization as the continuity roadmap where applicable.
12. Separate current Oracle Linux 9/10 KVM guidance from Oracle Linux Virtualization Manager. Existing OLVM estates must verify the exact Oracle Linux 8/OLVM legacy support boundary and must not infer OLVM as the current Oracle Linux 9/10 management plane.
13. Use `SOURCE_REVIEWS.json` plus durable records under `source-reviews/` as the repository source-review authority. Preserve explicit `NotRun`/`Blocked` states rather than inferring currency from package modification dates.

## Optional improvements

- Adopt the collection-level skill routers for language, framework, platform, virtualization, operating-system, and networking selection.
- Use `tools/generate-manifest/generate_manifest.py` with project-manifest `1.1.0` when infrastructure package selection should be explicit and machine-readable.
- Use `tools/compose-agents/compose_agents.py` to build a traceable standards bundle for the selected packages.
- Record source commit, package selection, validation output, and local tailoring with completion evidence.

## Compatibility assumptions

- Existing stable file paths and tool entry points remain present unless separately documented.
- Existing project-manifest `1.0.0` instances remain valid when the new infrastructure arrays are not used.
- Existing .NET package adoption remains valid; the new C# package separates language semantics from SDK/runtime concerns rather than replacing .NET guidance.
- The project name **Public Access Agents** remains valid even though the canonical GitHub repository slug is `Public-AI-Governance`.
- Release archive names remain `Public-Access-Agents-<VERSION>`.

## Validation

After `v0.10.0` is deliberately prepared and published, validate an adopting project against the exact selected source boundary. At minimum, re-run applicable tests, link checks, schema validation, manifest/composition validation, and project-specific review.

Repository release preparation uses:

```bash
python -m pip install --require-hashes -r tools/validate-schemas/requirements.lock
python tools/validate-all/run_all.py --include-tests
python tools/release/validate_release.py --tag v0.10.0
python tools/release/build_release.py --tag v0.10.0 --output-dir dist --force
```

These commands do not themselves create a tag or publish a GitHub Release.

## Downgrade and rollback

Rollback should restore the exact previously recorded source commit, tag, or copied bundle.

If an adopter changes persisted schema `$id` references for `0.10.0`, rollback must restore both the earlier schema content and the identifiers expected by that adopter's automation.

Do not use the nonexistent `v0.9.0` tag as a rollback target.

## Known limitations

- `0.10.0` remains unpublished until a final candidate commit is validated, reviewed, tagged, and released.
- Live vendor/platform compatibility cannot be established by repository validation alone.
- Most standards packages remain `baseline`, not `stable`.
- A successful repository validation does not certify an adopting project's security, correctness, compliance, or production readiness.
